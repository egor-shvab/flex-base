## 2. Общая оценка проекта

### Текущее техническое состояние

Проект в хорошем инженерном состоянии, заметно выше среднего для своего размера (~25 тыс. строк
без тестов). Архитектура продумана и последовательно соблюдается, ключевые инварианты закреплены
линтером и тестами, а решения задокументированы с обоснованием и отвергнутыми альтернативами.
Основные риски сосредоточены не в структуре кода, а в **нескольких местах взаимодействия
метаданных с физическим хранилищем** (общая таблица `Record` с JSONB, индексы по выражениям,
повторное использование ключей полей), а также в **эксплуатационной безопасности** (секрет JWT,
защита от перебора, заголовки).

### Сильные стороны

- **Доступ проверяется в самом запросе.** `requireMembership` + handler-фабрики
  (`server/utils/handler.ts`) делают невозможным маршрут внутри workspace без проверки членства;
  это закреплено правилом ESLint. 404 вместо 403 для чужих ресурсов — последовательно.
- **Единый источник правил антиэскалации** (`shared/utils/permissions.ts`) для сервера и клиента.
- **Реестры типов полей** — тотальные `Record<TFieldType, …>`, новый тип не скомпилируется, пока
  его не объявят все три слоя; разделение по бандлам обосновано.
- **Безопасный SQL**: везде параметризованный `Prisma.sql`; единственное место с DDL без параметров
  защищено `assertSafeKey`. Экранирование `%`/`_` в `ILIKE`. Защита от `undefined` в `where`
  (`routeParam` → `''`).
- **Продуманная обработка ошибок**: структурная редакция error log, отдельный неблокирующий путь
  для фоновых сбоев, защищённый публичный эндпоинт `/api/client-errors`.
- **Гонки учтены там, где о них подумали**: регистрация без pre-check, принятие приглашения через
  удаление строки в транзакции, повтор транзакции при коллизии `publicId`, guard в `where` при
  передаче владения, защита сторов от ответов «чужого» workspace.
- **Тестовая инфраструктура**: четыре проекта с ясным правилом выбора, колокация спецификаций,
  axe и target-size в e2e, защита от запуска разрушающих тестов против не-тестовой БД.

### Основные системные недостатки

1. **Общая физическая таблица `Record` не изолирует таблицы/воркспейсы на уровне выражений**:
   индексы по полю строятся по всем записям всех арендаторов, приведения типов (`::numeric`,
   `::boolean`) применяются к чужим данным. Отсюда критический дефект C-1 и серьёзный H-1.
2. **Жизненный цикл данных поля неполон**: удаление поля не очищает значения в `Record.data`, а ключ
   может быть переиспользован полем другого типа (H-1).
3. **Непоследовательность в борьбе со стоимостью `COUNT(*)`**: список записей ограничен 1000, а
   счётчики в сайдбаре считаются без ограничения на каждый запрос и после каждой записи (H-2).
4. **Эксплуатационная безопасность не доведена до продакшн-уровня**: секрет JWT вычисляется на этапе
   сборки, нет ограничения попыток входа, нет защитных HTTP-заголовков, нет отзыва сессий.
5. **Конкурентность на клиенте и в записи данных**: нет защиты от гонок ответов списка записей и от
   потерянных обновлений при одновременном редактировании.

## 3. Критические замечания (Critical)

### ✅ C-1. Индекс по полю строится по всем записям всех таблиц и приводит значения к типу — запись в чужой таблице может начать падать

- **Приоритет:** Critical
- **Категория:** надёжность, безопасность (изоляция арендаторов), производительность
- **Статус:** ✅ **Исправлено.** Каждый индекс создаётся частичным на таблице поля
  (`server/db/field-indexes.ts`), `tableId` проверяется перед инлайном в DDL; NUMBER и BOOLEAN
  приводят значение через `jsonCast` (`server/db/field-types/fragments.ts`) — значение другого
  JSON-типа читается как NULL. Старый индекс без предиката считается невалидным и пересобирается
  (`syncFieldIndexes` / `reconcileFieldIndexes`). Добавлены интеграционные тесты «чужие данные» и
  «неверный тип в своей таблице». Остаток: в уже развёрнутой базе пересборку запускает только
  `reconcileFieldIndexes`, который вызывает лишь сид (см. L-10). Исходная оценка: подтверждено
  анализом кода и семантики PostgreSQL.
- **Расположение:**
  - `server/db/field-indexes.ts:115-125` — `buildCreateIndexStatement`;
  - `server/db/field-indexes.ts:55` — `toIndexExpression`;
  - `server/db/field-types/number.ts:7` — `expr: (data ->> key)::numeric`;
  - `server/db/field-types/boolean.ts:7` — `expr: (data ->> key)::boolean`.
- **Проблема:** `CREATE INDEX CONCURRENTLY … ON "Record" ("tableId", (<expr>) …)` создаётся **без
  условия `WHERE "tableId" = '<id>'`**. Таблица `Record` общая для всех таблиц всех воркспейсов, а
  ключ поля — это slug имени (`price`, `amount`, `active`, `status`), который в разных таблицах
  совпадает. Для NUMBER выражение индекса — `(data ->> 'price')::numeric`, для BOOLEAN —
  `::boolean`.
- **Причина:** PostgreSQL вычисляет выражение индекса для **каждой** вставляемой/обновляемой строки
  таблицы, независимо от того, к какой «логической» таблице она относится. Если в любой другой
  таблице (в том числе в другом воркспейсе) есть TEXT-поле с тем же ключом и значением `"abc"`,
  вычисление `'abc'::numeric` выбрасывает `invalid input syntax for type numeric`.
- **Последствия:**
  1. Пока индекс существует, **любая** вставка или изменение записи с нечисловым значением под этим
     ключом в любой таблице любого воркспейса падает с 500. Один пользователь, включивший индекс на
     своём поле, ломает запись данных у других арендаторов (межарендаторский отказ в обслуживании,
     в том числе непреднамеренный).
  2. Если такая строка уже есть, построение индекса падает; ошибка уходит только в лог
     (`limitations.md` это признаёт для «сбоя построения», но не для этой причины), пользователь
     видит «успех».
  3. Каждый индекс содержит запись для **каждой** строки `Record` (включая NULL для чужих таблиц),
     т.е. размер и стоимость поддержки индекса пропорциональны объёму всей БД, а не таблицы.
- **Предложение:**
  - Строить **частичные** индексы: `… ON "Record" ((<expr>) …) WHERE "tableId" = '<tableId>'`
    (cuid безопасен для инлайна, но его тоже стоит прогнать через проверку формата, как ключ).
    Ведущий столбец `"tableId"` тогда не нужен. Планировщик сопоставит частичный индекс, так как
    запрос планируется на Bind с конкретным `tableId` — тот же механизм, на который проект уже
    опирается.
  - Независимо от этого сделать приведение безопасным: `CASE WHEN jsonb_typeof(data -> key) =
'number' THEN (data ->> key)::numeric END` (аналогично для boolean), и использовать одно и то же
    выражение в запросе и в DDL.
  - Добавить интеграционный тест: индексированное NUMBER-поле в таблице A + TEXT-поле с тем же
    ключом в таблице B → вставка в B успешна.

## 4. Серьёзные замечания (High)

### ✅ H-1. Значения удалённого поля остаются в записях, а ключ переиспользуется новым полем другого типа

- **Приоритет:** High
- **Категория:** надёжность, целостность данных
- **Статус:** ✅ **Исправлено.** `FieldService.deleteField` удаляет поле и очищает его ключ в
  записях таблицы (`clearFieldValues`) одной транзакцией, поэтому освободившийся ключ новое поле
  получает пустым. Миграция `20261114120000_clear_deleted_field_values` удаляет значения полей,
  удалённых до исправления (на dev-базе — 7 записей в Deals). Цена — синхронная перезапись строк
  таблицы при удалении поля — записана в `docs/limitations.md`. Исходная оценка: подтверждено.
- **Расположение:** `server/services/fields.ts:145` (`deleteField`), `server/services/fields.ts:68`
  (`buildFieldKey` по живым полям), `server/utils/field-key.ts` (`buildFieldKey`),
  `server/db/field-types/number.ts:7`, `boolean.ts:7`.
- **Проблема:** `deleteField` удаляет только строку `Field`; значения под его ключом остаются в
  `Record.data` всех записей. `buildFieldKey` проверяет уникальность только среди **текущих**
  полей, поэтому новое поле с тем же именем получает тот же ключ.
- **Причина:** нет ни очистки данных при удалении, ни «надгробий» для использованных ключей.
- **Последствия:** сценарий «удалить TEXT-поле _Amount_ → создать NUMBER-поле _Amount_»:
  - старые строки отображаются в новом поле как его значения (неверный тип в ячейке и форме);
  - фильтр или сортировка по новому полю выполняют `(data->>'amount')::numeric` для строк таблицы и
    **падают с 500 для всей таблицы**, пока каждая старая запись не будет пересохранена (при
    сохранении zod-схема отрежет лишние ключи, но значение под тем же ключом будет отклонено как
    не-число, т.е. пользователь не сможет сохранить запись, не очистив поле);
  - потенциально: при seq scan PostgreSQL не гарантирует порядок вычисления `AND`, поэтому
    приведение может выполниться и для строк других таблиц;
  - «мёртвые» значения навсегда занимают место и попадают в `record_search_text`.
- **Предложение:**
  - при удалении поля в фоне очищать ключ пакетами (`UPDATE "Record" SET data = data - key WHERE
"tableId" = … AND data ? key`, порциями по N строк);
  - или исключить переиспользование: хранить использованные ключи таблицы (поле `Table.retiredKeys`
    или мягкое удаление `Field.deletedAt`) и учитывать их в `buildFieldKey`;
  - в любом случае — безопасное приведение типов из C-1.

### ✅ H-2. Счётчик записей в сайдбаре — неограниченный `COUNT(*)` на каждый запрос и после каждой записи

- **Приоритет:** High
- **Категория:** производительность, масштабируемость
- **Статус:** ✅ **Исправлено.** Новый столбец `Table.recordCount` (миграция
  `20261114140000_table_record_count`: nullable → backfill → NOT NULL) меняют `createRecord`
  (тем же `UPDATE`, что и `recordCounter`) и `deleteRecord` (в одной транзакции с удалением, только
  если строка нашлась); `tableListSelect` читает его вместо `_count.records`, формат ответа прежний.
  Бэкфилл на dev-базе совпал с `COUNT(*)` по всем 26 таблицам; проверено интеграционными тестами и в
  приложении (счётчик Ideas 0 → 1 → 0). Правило «любой новый путь записи двигает счётчик» записано в
  `docs/decisions.md`. Исходная оценка: подтверждено.
- **Расположение:** `server/db/tables.ts:26` (`_count: { fields, records }`),
  `server/services/tables.ts:14` (`listTables`), `server/services/tables.ts:24` (`getTableListRow`),
  маршруты `records/index.post.ts`, `records/[recordAddress].delete.ts`, `fields/index.post.ts`;
  отображение — `app/components/app/AppSidebar.vue:49`.
- **Проблема:** `listTables` вызывается layout'ом на каждой загрузке страницы воркспейса и
  выполняет точный `COUNT(*)` записей **по каждой таблице**. `getTableListRow` повторяет точный
  подсчёт после каждого создания и удаления записи.
- **Причина:** проект сам признаёт, что точный подсчёт — `O(rows)`, и ради этого ограничил счётчик
  в списке записей 1000 (`RECORD_COUNT_CAP`, `decisions.md` → _The count is bounded…_). Сайдбар это
  ограничение обходит.
- **Последствия:** время загрузки любой страницы воркспейса и время каждой записи растут линейно с
  суммарным объёмом данных (при сотнях тысяч записей на таблицу — десятки–сотни мс на таблицу,
  умножить на число таблиц). Создание записей пакетами конкурирует со сканированиями.
- **Предложение:** вести счётчик в `Table` (`recordCount`), изменяемый в той же транзакции, что и
  `recordCounter` при создании, и при удалении (одна строка уже блокируется), либо применять тот же
  ограниченный подзапрос `LIMIT CAP+1` и показывать `1000+`. Для полей (`_count.fields`) подсчёт
  дешёвый и может остаться.

### ✅ H-3. Секрет JWT вычисляется на этапе сборки; переменная из README в рантайме не действует

- **Приоритет:** High
- **Категория:** безопасность, конфигурация
- **Статус:** ✅ **Исправлено.** `runtimeConfig.jwtSecret` по умолчанию пустой и заполняется при
  старте из `NUXT_JWT_SECRET`; плагин `server/plugins/jwt-secret.ts` (`assertJwtSecret`) не даёт
  серверу стартовать с пустым или коротким (< 32 символов) секретом. Переменная переименована в
  `.env`, `.env.example`, README, CLAUDE.md и тестовых конфигах; мёртвые `JWT_SECRET` из CI убраны.
  Проверено: в `.output` нет секрета; собранный сервер без секрета, с коротким и со старым
  `JWT_SECRET` не стартует, с `NUXT_JWT_SECRET` — стартует; e2e на сборке проходят. Исходная
  оценка: потенциальный риск.
- **Расположение:** `nuxt.config.ts:40` (`jwtSecret: process.env.JWT_SECRET || ''`), `README.md`
  (таблица переменных), `scripts/preview.mjs`, `.github/workflows/ci.yml` (`JWT_SECRET:
ci-not-a-real-secret` при сборке).
- **Проблема:** значение по умолчанию в `runtimeConfig` вычисляется при `nuxt build` и
  сериализуется в серверный бандл. В рантайме Nuxt переопределяет его только переменной
  **`NUXT_JWT_SECRET`**; `JWT_SECRET`, которую документирует README, на собранное приложение не
  влияет. Плюс фолбэк на пустую строку и отсутствие проверки при старте.
- **Причина:** смешение build-time и runtime конфигурации.
- **Последствия:** артефакт, собранный с одним секретом (например, CI-заглушкой), при развёртывании
  с «правильной» `JWT_SECRET` продолжит подписывать и принимать токены, подписанные известным
  секретом, → возможна подделка JWT для любого `userId` (полный обход аутентификации). При пустом
  секрете `jsonwebtoken` бросает исключение — вход ломается с 500 без понятной диагностики.
- **Предложение:** объявить `runtimeConfig: { jwtSecret: '' }` без чтения `process.env`;
  документировать `NUXT_JWT_SECRET`; в серверном плагине при старте проверять, что секрет задан и
  достаточно длинный (например, ≥ 32 байта), и падать при старте иначе.

### ✅ H-4. Нет защиты от перебора паролей и массовой регистрации

- **Приоритет:** High
- **Категория:** безопасность
- **Статус:** ✅ **Исправлено.** `login.post.ts` ограничивает попытки по адресу сокета (100 за 15
  минут) и по email в нижнем регистре (10 за 15 минут), проверка идёт до bcrypt; `register.post.ts`
  — 30 регистраций в час с адреса. Общие `assertWithinRateLimit` и `toClientAddress` в
  `server/utils/rate-limit.ts`, ими же пользуются client-errors и приглашения. Проверено
  интеграционными тестами и в приложении (форма показывает «Too many sign-in attempts…»). Остаток
  записан в `docs/limitations.md`: лимиты в памяти процесса, за обратным прокси адрес общий,
  per-email лимит позволяет на 15 минут закрыть вход в чужой аккаунт. Исходная оценка: подтверждено.
- **Расположение:** `server/api/auth/login.post.ts`, `server/api/auth/register.post.ts`,
  `server/services/auth.ts`.
- **Проблема:** публичные эндпоинты входа и регистрации не ограничены по частоте ни по IP, ни по
  email, хотя в проекте уже есть `createRateLimiter` (используется для client-errors и приглашений).
- **Причина:** ограничения добавлялись точечно, вход не был включён.
- **Последствия:** неограниченный онлайн-перебор паролей (минимум 8 символов, без требований к
  сложности); CPU-нагрузка от bcrypt (cost 10 ≈ десятки мс на запрос) — дешёвый способ нагрузить
  сервер; массовая регистрация создаёт для каждого аккаунта workspace + 3 роли + membership.
  Неограниченная регистрация также обесценивает лимит приглашений «на пользователя».
- **Предложение:** rate limit на вход по IP и по нормализованному email (например, 10 попыток / 15
  минут) и на регистрацию по IP; при многоинстансной развёртке — общий стор (это уже отмечено в
  `limitations.md` для существующих лимитов). Опционально — прогрессивная задержка.

### ✅ M-1. Тайминг входа раскрывает существование email

- **Приоритет:** Medium
- **Категория:** безопасность
- **Статус:** ✅ **Исправлено.** `authenticateUser` всегда вызывает `verifyPassword`: для неизвестного
  email — против `UNMATCHED_PASSWORD_HASH` (хеш той же стоимости, `server/utils/auth.ts`). Unit-тест,
  закреплявший старое поведение («без сравнения пароля»), переписан. Исходная оценка: подтверждено.
- **Расположение:** `server/services/auth.ts:55-59` (`authenticateUser`).
- **Проблема:** для неизвестного email функция возвращает 401 сразу, не вычисляя bcrypt; для
  известного — после `bcrypt.compare` (~50–100 мс).
- **Причина:** сообщения об ошибке одинаковы, но время ответа — нет. Для регистрации проект
  тайминг учёл явно (`decisions.md` → _Registration has no uniqueness pre-check_), для входа — нет.
- **Последствия:** перечисление зарегистрированных адресов по времени ответа, что противоречит
  заявленной цели «no user enumeration» и облегчает H-4.
- **Предложение:** при отсутствии пользователя сравнивать пароль с заранее вычисленным фиктивным
  хешем того же cost.

### ✅ M-2. Сессию невозможно отозвать

- **Приоритет:** Medium
- **Категория:** безопасность
- **Статус:** ✅ **Исправлено.** Столбец `User.sessionVersion` (миграция
  `20261114150000_user_session_version`) попадает в токен как `ver`; `findAuthUser` ищет пользователя
  по `id` **и** версии в одном запросе, `logout` увеличивает версию (`AuthService.revokeSessions`).
  Выход завершает сессии на всех устройствах — цена одного счётчика вместо таблицы сессий. Токены
  без `ver`, выданные до исправления, отклоняются: после деплоя все войдут заново один раз.
  Проверено интеграционными и e2e-тестами (выход на одном «устройстве» разлогинивает другое) и в
  приложении (сессия curl получила 401 после выхода в браузере). Исходная оценка: подтверждено.
- **Расположение:** `server/utils/auth.ts` (`signAuthToken`, TTL 7 дней),
  `server/api/auth/logout.post.ts`, `server/middleware/auth.ts`.
- **Проблема:** выход только удаляет cookie у клиента; токен остаётся действительным до истечения
  7 дней. Механизма инвалидации (версия сессии у пользователя, `iat` против `passwordChangedAt`,
  список отзыва) нет.
- **Причина:** полностью stateless JWT.
- **Последствия:** украденная cookie (общий компьютер, утечка через расширение) действует неделю
  даже после «выхода»; при появлении смены пароля она не завершит другие сессии.
- **Предложение:** добавить `User.sessionVersion` (или `tokensValidAfter`), класть его в токен и
  сверять в middleware — запрос пользователя там уже выполняется, так что стоимость нулевая;
  выход/смена пароля увеличивают версию. Дополнительно — укоротить TTL со скользящим продлением.

### ✅ M-3. Гонка ответов при перезагрузке списка записей

- **Приоритет:** Medium
- **Категория:** надёжность, асинхронность
- **Статус:** ✅ **Исправлено.** Новый `createLatestRequest` (`app/utils/latest-request.ts`)
  прерывает предыдущий запрос и отбрасывает ответ, пришедший после более нового; `fetchRecords`
  передаёт его `signal` в `api.list`. `useSelectOptions` переведён на ту же утилиту (DRY). Проверено
  тестом стора: медленная первая страница, ответившая после второй, не перезаписывает её. Исходная
  оценка: подтверждено.
- **Расположение:** `app/pages/w/[workspaceAddress]/tables/[tableAddress]/index.vue:249`
  (`watch(queryKey, …)`), `app/stores/records.ts` (`fetchRecords`).
- **Проблема:** каждое изменение фильтра/сортировки/страницы запускает `fetchRecords` без отмены
  предыдущего запроса и без проверки «это ответ на последний запрос». Тот же шаблон в проекте уже
  реализован правильно в `BaseSelect/useSelectOptions.ts` (`requestId` + `AbortController`).
- **Причина:** поиск дебаунсится, но клики по сортировке, пагинации и фильтрам — нет; медленный

- **Последствия:** таблица показывает строки, не соответствующие URL и заголовкам (например,
  отсортированные по старой колонке), `status` становится `ready` от устаревшего ответа.
- **Предложение:** счётчик запросов в сторе (игнорировать ответ, если он не последний) и
  `AbortSignal`, передаваемый в `api.list`. Вынести шаблон «последний запрос побеждает» в общий
  util, раз он нужен второй раз (правило DRY проекта).

### ◐ M-4. Потерянные обновления при одновременном редактировании

- **Приоритет:** Medium
- **Категория:** надёжность, целостность данных
- **Статус:** ◐ **Исправлено для записей.** Клиент отправляет `If-Match: "<updatedAt>"` той версии, на которой
  открыта форма; `parseRecordVersion` (`server/utils/record-version.ts`) читает его, а
  `RecordService.updateRecord` кладёт версию в `where` обновления, так что проверка и запись — один
  оператор. Промах различается потом: запись есть — 412 с понятным сообщением, нет — 404. Стор при
  412 обновляет список. Формат тела не изменился; без заголовка запись безусловна. Проверено
  интеграционным тестом (из двух сохранений одной версии второе получает 412, первое сохраняется) и в
  приложении (форма показала конфликт, после повторного открытия сохранение прошло). 412 добавлен в
  правила статус-кодов `CLAUDE.md`. Исходная оценка: подтверждено.
  **Остаток:** `updateField` и `updateRole` по-прежнему сохраняют без проверки версии —
  тот же приём (`If-Match` + версия в `where`) применим к ним.
- **Расположение:** `server/services/records.ts` (`updateRecord` — `data` заменяется целиком),
  `server/services/fields.ts` (`updateField`), `server/services/roles.ts` (`updateRole`).
- **Проблема:** запись сохраняется целиком без проверки версии. Два участника, открывшие одну
  запись, молча перезапишут изменения друг друга (в том числе в разных полях).
- **Причина:** нет оптимистической блокировки; `updatedAt` уже есть и мог бы служить версией.
- **Последствия:** тихая потеря данных в многопользовательском workspace — основном сценарии после
  внедрения участников и ролей.
- **Предложение:** передавать с формы `updatedAt` (или целочисленную `version`) и обновлять
  `WHERE id = … AND "updatedAt" = …`; при 0 изменённых строк — 409 с предложением перезагрузить.
  Real-time при этом не требуется.

### ✅ M-5. Нет ограничения размера тела запроса для публичных и прочих JSON-эндпоинтов

- **Приоритет:** Medium
- **Категория:** безопасность (DoS)
- **Статус:** ✅ **Исправлено.** `server/middleware/body-limit.ts` через общий `assertBodyWithin`
  (`server/utils/request-body.ts`) отклоняет тело `/api/**` больше 1 МиБ (413) и chunked-тело без
  `content-length` (411) по заголовкам, до чтения; `client-errors` использует ту же функцию со своим
  лимитом 16 КБ. Проверено unit- и e2e-тестом и запросами к dev-серверу. Лимит выбран с запасом:
  запись с десятками текстовых полей по 1000 символов укладывается. Исходная оценка: потенциальный
  риск.
- **Расположение:** все маршруты с `readValidatedBody`, в первую очередь неаутентифицированные
  `auth/login.post.ts`, `auth/register.post.ts`.
- **Проблема:** только `/api/client-errors` проверяет `content-length`. Остальные эндпоинты
  буферизуют тело любого размера до валидации zod (у пароля нет `max`).
- **Причина:** защита сделана локально для одного эндпоинта.
- **Последствия:** анонимные запросы на десятки мегабайт расходуют память и CPU (парсинг JSON).
- **Предложение:** общий серверный middleware с лимитом (например, 64–256 КБ для `/api/**`, с
  исключениями при необходимости), отказ 413/411; либо лимит на уровне обратного прокси,
  зафиксированный в документации развёртывания.

### ✅ M-6. Отсутствуют защитные HTTP-заголовки

- **Приоритет:** Medium
- **Категория:** безопасность
- **Статус:** ✅ **Исправлено.** `routeRules` в `nuxt.config.ts` ставят на все ответы

- **Расположение:** `nuxt.config.ts` (нет `routeRules`/`headers`), `server/` (нет middleware

- **Последствия:** приложение можно встроить во фрейм (clickjacking на «Delete workspace»,

- **Предложение:** `routeRules: { '/**': { headers: { … } } }` или модуль `nuxt-security`; CSP

### ✅ M-7. Нестабильный порядок строк при пагинации

- **Приоритет:** Medium
- **Категория:** надёжность
- **Статус:** ✅ **Исправлено.** Все порядки в `record-sql.ts` (список, сортировка по полю, опции
  связи) заканчиваются на `"number"` — он уникален в таблице. Табличный индекс заменён на
  `("tableId", "createdAt", "number")` двумя миграциями с `CONCURRENTLY`; B-tree индексы полей
  оканчиваются на `"createdAt" DESC, "number" DESC`. Чтобы существующие индексы полей пересобрались,
  введена метка формы (`INDEX_SHAPE` в комментарии индекса) вместо частной проверки предиката из C-1;
  на dev-базе `reconcileFieldIndexes` пересобрал 29 индексов. Проверено: 7 записей с одним
  `createdAt` и значением проходят по страницам ровно по разу; план default-порядка читает новый
  индекс без шага сортировки; в приложении 212 задач по 5 страницам без повторов. Исходная оценка:
  подтверждено.
- **Расположение:** `server/db/record-sql.ts:108` (сортировка по умолчанию `ORDER BY "createdAt"`),
  `:116` (тай-брейк `"createdAt" DESC`), `:122-124` (опции связи),
  `server/db/field-indexes.ts` (B-tree заканчивается `"createdAt"`).
- **Проблема:** финальный ключ сортировки — `createdAt`, который не уникален (записи из одной
  транзакции, импорта, сида или созданные в одну миллисекунду совпадают).
- **Причина:** нет уникального тай-брейка.
- **Последствия:** при `LIMIT/OFFSET` строки с равным `createdAt` могут повторяться на соседних
  страницах или пропадать; порядок «прыгает» между обновлениями.
- **Предложение:** добавлять последним ключом `"number"` (уникален в таблице, монотонен) — `…,
"createdAt" DESC, "number" DESC` — и включить его в состав индексов `(tableId, createdAt)` и
  индексов полей, чтобы не потерять index-only порядок.

### ✅ M-8. Для подписи связанных записей читается весь JSONB целевых записей

- **Приоритет:** Medium
- **Категория:** производительность
- **Статус:** ✅ **Исправлено.** `listTargetRecords` и `listRelationOptions` выбирают
  `data -> labelFieldKey AS label` вместо всего `data`; запросы сгруппированы по паре «целевая
  таблица + поле подписи», так что их число не зависит от числа строк. `listRecords` передаёт и
  разрешённый фильтр, поэтому чип фильтра получает подпись, даже когда ни одна строка страницы на
  запись не ссылается. Проверено unit- и интеграционными тестами (включая мульти-значное поле
  подписи) и в приложении: ответ опций содержит только id, номер и подпись. Исходная оценка:
  подтверждено.
- **Расположение:** `server/services/relations.ts:73` (`listTargetRecords`: `select: { id, number,
data }`), `server/services/relations.ts:204` (`listRelationOptions`: `SELECT id, "number", data`).
- **Проблема:** для отображения одной подписи (`data ->> labelFieldKey`) загружается весь документ
  записи: до 100 строк × число RELATION-полей на каждой странице и до 200 строк на каждый список
  опций.
- **Причина:** использован типовой `findMany` вместо проекции.
- **Последствия:** лишний трафик БД ↔ Node и парсинг JSON, растущие с «шириной» целевых таблиц
  (TOAST-распаковка больших документов).
- **Предложение:** выбирать только нужное: `SELECT id, "number", data ->> $key AS label` (при
  нескольких полях с разными `labelFieldKey` к одной таблице — `jsonb_build_object` из нужных
  ключей или отдельный запрос на ключ).

### ✅ M-9. Опции всех связей загружаются при каждом открытии таблицы

- **Приоритет:** Medium
- **Категория:** производительность, избыточные запросы
- **Статус:** ✅ **Исправлено.** Страница только сообщает стору, у какой таблицы спрашивать
  (`setOptionSource`); `RelationFieldSelect` при первом монтировании вызывает

  открытие Tasks (3 поля-связи) больше не запрашивает опций, они приходят при открытии формы.
  Исходная оценка: подтверждено.
- **Расположение:** `app/pages/w/[workspaceAddress]/tables/[tableAddress]/index.vue:241`

- **Проблема:** на SSR-загрузке страницы для каждого RELATION-поля выполняется отдельный запрос

- **Причина:** опции служат и кэшем подписей, и источником для селектов.
- **Последствия:** время первого рендера и нагрузка на БД растут с числом связей, даже если

## 6. Незначительные улучшения (Low)

### ✅ L-1. Любая ошибка `/api/auth/me` трактуется как «не вошёл»

- **Категория:** надёжность, UX · **Статус:** ✅ **Исправлено** — `fetchUser` считает выходом только 401, другую ошибку бросает и
  оставляет стор неинициализированным; middleware показывает страницу ошибки (503 без ответа).
- **Расположение:** `app/stores/auth.ts:20` (`catch { user.value = null }`),
  `app/middleware/auth.global.ts`.
- **Проблема / последствия:** сетевой сбой или 500 (например, кратковременная недоступность БД при
  SSR) отправляет авторизованного пользователя на `/auth/login`, а `isInitialized = true` не даёт
  повторить попытку без перезагрузки.
- **Предложение:** различать 401 (не вошёл) и прочие ошибки; для прочих — страница ошибки с
  повтором.

### ✅ L-2. Удаление поля-подписи не защищено и не обрабатывается

- **Категория:** целостность метаданных · **Статус:** ✅ **Исправлено.** Проверка вынесена в
  `RelationService.assertNotRelationTarget` (общая с удалением таблицы); удаление поля, которое
  RELATION-поле показывает как подпись, отклоняется с 409 `"<поле>" in "<таблица>" shows this field
as its label` — проверено в приложении.
- **Расположение:** `server/services/fields.ts:145` (`deleteField`) против
  `server/services/tables.ts` (`assertNotRelationTarget` — аналогичная защита для таблиц есть).
- **Проблема / последствия:** если удалить поле, на которое ссылается `options.labelFieldKey`
  RELATION-поля в другой таблице, связь молча начинает показывать номера вместо подписей, а форма
  настройки поля показывает невалидное значение. Пользователь не получает предупреждения.
- **Предложение:** при удалении искать RELATION-поля с этим `labelFieldKey` и целевой таблицей и
  возвращать 409 (как для таблиц) либо переключать их подпись на другое поле.

### L-3. Правило «подписью связи не может быть RELATION» проверяется только на клиенте

- **Категория:** валидация · **Статус:** Подтверждено
- **Расположение:** `server/utils/table-access.ts` (`requireFieldTarget` проверяет лишь
  существование ключа); правило описано в `docs/architecture.md` §6.
- **Проблема / последствия:** прямой API-запрос может назначить подписью RELATION-поле, и подпись
  будет cuid'ом — нарушение документированного контракта.
- **Предложение:** в `requireFieldTarget` проверять `type !== 'RELATION'` у выбранного поля.

### L-4. TOCTOU в проверках антиэскалации

- **Категория:** безопасность · **Статус:** Потенциальный риск (нужны конкурентные действия двух
  администраторов)
- **Расположение:** `server/services/members.ts` (`changeMemberRole`, `removeMember`),
  `server/services/roles.ts` (`updateRole`, `deleteRole`).
- **Проблема:** права проверяются по строке, прочитанной до записи; `where` записи не повторяет
  условие (роль участника или права роли могли измениться между чтением и записью). Это
  противоречит собственному принципу проекта «ownership lives in the where clause».
- **Последствия:** узкое окно, в котором менее привилегированный участник может изменить/удалить
  участника, только что повышенного до роли вне его прав.
- **Предложение:** добавить в `where` прочитанный `roleId` участника (для ролей — сравнение
  `permissions`), при 0 строк — 409/повтор.

### ✅ L-5. Кэш связей в сторе растёт без ограничений и хранится глубоко реактивным

- **Категория:** производительность, память · **Статус:** ✅ **Исправлено** — кэши стора на `shallowRef`, новые записи дописываются на
  месте с `triggerRef`; `fetchRecords` при смене таблицы вызывает `relations.clearState()`.
  Решение «merge-only на всю сессию» в `docs/decisions.md` переписано.
- **Расположение:** `app/stores/relations.ts` (`linkedByField`, `linkedByFieldNumber`,
  `optionsByField` — `ref`, никогда не очищаются; `cacheLinkedRecords` копирует весь словарь поля
  при каждом вызове).
- **Последствия:** в долгой сессии со множеством таблиц память и стоимость каждой загрузки страницы
  растут; противоречит правилу §7 (`shallowRef` для больших коллекций).
- **Предложение:** `shallowRef` + очистка при смене workspace/таблицы (по аналогии с
  `loadedWorkspaceAddress` в других сторах), мутировать вложенный объект поля вместо копирования.

### ✅ L-6. Выход не сбрасывает состояние Pinia

- **Категория:** безопасность (клиент), надёжность · **Статус:** ✅ **Исправлено** — `logout` завершается `reloadNuxtApp({ path: '/auth/login' })`;
  проверено в приложении (состояние окна не пережило выход).
- **Расположение:** `app/stores/auth.ts` (`logout`).
- **Проблема / последствия:** только `workspaces` проверяет `loadedUserId`; `tables`, `records`,
  `members`, `roles`, `invitations`, `relations`, `fields` сохраняют данные предыдущего
  пользователя до следующей загрузки. На общем компьютере следующий пользователь может кратко

- **Предложение:** после выхода — полная перезагрузка (`reloadNuxtApp` / `window.location`) или

### L-7. Списки участников, приглашений и таблиц не пагинируются

- **Категория:** масштабируемость · **Статус:** Потенциальный риск
- **Расположение:** `server/services/members.ts` (`listMembers`), `server/services/tables.ts`

- **Проблема:** участники и таблицы возвращаются целиком (у ролей и приглашений есть лимиты, у

### L-8. `options` поля приводится к типу без проверки

- **Категория:** типизация · **Статус:** Подтверждено

### L-9. Гонка при одновременном создании полей

- **Категория:** надёжность · **Статус:** Потенциальный риск
- **Расположение:** `server/services/fields.ts:56-68` (`createField`).
- **Проблема / последствия:** `key` и `order` вычисляются из прочитанного списка; два параллельных
  создания получают одинаковый `order` (порядок колонок недетерминирован) или одинаковый `key`, и

- **Предложение:** повторять создание при `P2002` на `(tableId, key)` с пересчётом ключа; `order`
  брать атомарно (`SELECT max(order)+1` в транзакции с блокировкой таблицы или счётчиком).

### L-10. Фоновые DDL индексов для одного поля могут пересекаться

- **Категория:** надёжность · **Статус:** Потенциальный риск
- **Расположение:** `server/services/fields.ts` (`syncIndexesInBackground` на каждом
  `updateField`), `server/db/field-indexes.ts` (`syncFieldIndexes`).
- **Проблема:** два быстрых изменения поля запускают два независимых `syncFieldIndexes`; один может

  что принятое в `limitations.md` «ошибка видна только в логе» — здесь итоговое состояние может не
  соответствовать последнему желаемому, и `reconcileFieldIndexes` нигде не вызывается.
- **Предложение:** сериализовать синхронизацию по `field.id` (in-process очередь или
  `pg_advisory_lock(hash(fieldId))`), либо вызывать `reconcileFieldIndexes` при старте сервера.

## 7. Архитектурные рекомендации

### Основные архитектурные недостатки

1. **Изоляция «логических таблиц» внутри физической `Record` держится на `WHERE "tableId" = …` в
   запросах, но не в выражениях и индексах.** Всё, что вычисляется по строке вне фильтра (индексы
   по выражениям, приведения типов при seq scan), видит данные всех арендаторов. Это корень C-1 и
   части H-1.
2. **Ключ поля — одновременно идентификатор данных и производная от имени**, при этом у ключа нет
   жизненного цикла (удаление не освобождает данные, ключ можно переиспользовать). Решение
   «ключ неизменяем» (`decisions.md`) защищает от переименования, но не от удаления/пересоздания.
3. **Денормализованные счётчики считаются агрегатами на чтении.** Для `recordCounter` проект уже
   использует счётчик в строке таблицы, а для числа записей — нет.
4. **Конфигурация безопасности распределена и неполна**: лимиты частоты — точечно в двух ручках,
   лимит тела — в одной, заголовков нет, секрет — build-time.

### Направления улучшения

- **Ввести «безопасное выражение значения» как контракт `IFieldSqlModule`.** Каждый тип
  объявляет `expr`, который никогда не бросает исключение на чужих данных (`CASE WHEN
jsonb_typeof(...)`). Добавить тест-инвариант в `server/db/field-types` для всех типов: выражение
  над строками с «чужими» значениями не падает. Это закрывает целый класс ошибок, а не только
  NUMBER/BOOLEAN.
- **Частичные индексы на таблицу** (`WHERE "tableId" = …`) как единственная форма индексов по
  полям. Заодно индекс станет меньше на порядки, а «HOT updates» будут теряться только у таблиц с
  индексами (проверить по `decisions.md` → _An index is opted into per field_).
- **Жизненный цикл поля**: мягкое удаление (`Field.deletedAt`) + фоновая очистка ключа + запрет
  повторного использования ключа до завершения очистки.
- **Единый серверный слой эксплуатационной безопасности**: один Nitro-плагин/middleware для лимита
  тела, заголовков и проверки конфигурации при старте; общая фабрика rate-limit-ов с подключаемым
  хранилищем (in-memory сейчас, Redis/Postgres позже — это уже требование из `limitations.md`).
- **Общий примитив «последний запрос побеждает»** для клиентских загрузок (сейчас корректно только в
  `useSelectOptions`).
- **Оптимистическая конкурентность** как общий механизм для изменяемых сущностей (записи, поля,
  роли) — `updatedAt` в теле, 409 при расхождении, единый обработчик на клиенте.

## 10. Итоговые выводы

- **Кодовая база зрелая**: архитектурные границы реальны и проверяются автоматически, доступ
  проверяется в запросах, документация объясняет «почему», тестовая стратегия продумана. Большая
  часть найденного — не следствие небрежности, а пограничные случаи модели «все таблицы в одной
  физической таблице с JSONB».
- **Главный риск — C-1**: опциональная функция индексации полей в нынешнем виде позволяет одному
  арендатору сломать запись данных у других. Исправление локальное (частичные индексы + безопасные
  приведения) и не меняет архитектуру.
- **Второй по важности блок — эксплуатационная безопасность** (H-3, H-4, M-1, M-2, M-5, M-6): к
  моменту реального развёртывания его нужно закрыть целиком; по объёму это несколько небольших
  изменений на входной границе сервера.
- **Производительность** в целом спроектирована внимательно (ограниченный счётчик, триграммный
  индекс, батчинг подписей), но два места выбиваются из собственных правил проекта: неограниченный
  `COUNT(*)` в сайдбаре (H-2) и загрузка полного JSONB ради одной подписи (M-8).
- **Перспективные направления:** формализовать контракт «безопасного выражения» для типов полей;
  ввести жизненный цикл поля (мягкое удаление и очистка); единый слой серверной защиты и
  подключаемое хранилище для лимитов (это также подготовит многоинстансное развёртывание);
  оптимистическая конкурентность как базовый механизм для многопользовательской работы.
